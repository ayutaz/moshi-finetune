## この計画が答える問い

M3 は不合格だった。判定は正しいが、**原因の読みは誤りだった**。
したがって M3-R は「M3 のやり直し」ではない。**M3 が答えられなかった問いに、
初めて答えられる状態を作る**ことが目的である。

答えるべき問いは 1 つ。

> **データ構造と学習率を文献・過去成功例に合わせたとき、J-Moshi-ext は
> つくよみちゃんの声に寄りながら対話能力を保てるか。**

M3 はこの問いを立てられていなかった。データが無音を教え、計器が音を見ず、
基準線が壊れていたためである。

## 第 2 段: データを作り直す（US$0 / 半日〜1 日）

**この段が最大の勝負どころである。** 検証記録が確定させた最有力の機序は
「**loss を下げる最短経路が無音だった**」であり、それを作ったのはデータ構造である。

### 現状と目標

| 項目 | M3 | 過去成功 run | M3-R の目標 |
| --- | ---: | ---: | --- |
| turn / 対話 | 3.00 | 6.12 | **5.0 以上** |
| A が話す回数 / 対話 | **1.00** | 約 3.06 | **2 以上** |
| 1 ターンの平均長 | 7.0 秒 | 3.1 秒 | 短くする |
| A が無音の時間 | 68.8% | — | 下げる |
| 系列長 | 21.0 秒 | — | **60 秒以上**（Kyutai 推奨 100〜300 秒）|
| 重なり | なし | — | **入れる** |
| 非発話チャンネル | デジタル無音 | — | **ルームトーン** |
| text の裸 `▁` | 45.5% | — | **3.6%**（フラグ付き） |
| train step 数 | 45 | 65 | **45 を維持** |

### 設計上の制約と、その解き方

train 文は 72 文しかない。**A のターン数を増やすと対話数が減り、step が落ちる。**

| A が話す回数 | train 対話 | 総 step | 系列長 |
| ---: | ---: | ---: | ---: |
| 1（M3 現行） | 72 | 45 | 21 秒 |
| 2（素朴に分割） | 36 | **25** | 46 秒 |
| 3 | 24 | **15** | 70 秒 |

**解: 文を読点で分割する。** train 72 文のうち **70 文（97%）が「、」を含み、63 文が 2 個以上**持つ。
1 文を 2 ターンに割れば、**対話数を 72 のまま**、A のターンを 2 回にできる。

```
現行:  B ──── A ──────── B                      3 turn / 21 秒
M3-R:  B ── A₁ ─ b ─ A₂ ──── B                  5 turn / 約 30 秒
              ↑ 短い相槌（「ええ」「なるほど」）
```

さらに以下を重ねる。

1. **ルームトーン** — 非発話チャンネルにコーパス収録の実際の無音区間を敷く。
   `pad ⟺ 無音` の 98% 一致を直接切る。**最も直接的で最も安い。**
2. **重なり** — A の発話終端と B の相槌を数百 ms 重ねる。full-duplex を教える。
3. **連結** — 対話を連結して系列長を 100 秒超へ。実装可否は 2-6 で判定する。

### 手順

| # | 作業 | ゲート |
| --- | --- | --- |
| 2-1 | `--no_whitespace_before_word` を付けて既存 parquet を作り直し、行単位で diff | row 1-16 が**バイト単位で不変**。text の裸 `▁` が 45.5% → 3.6% |
| 2-2 | 読点分割の台本を生成。分割点の自然さを全 72 文で目視確認 | 分割後の各ターンが 2 モーラ以上、文として読める |
| 2-3 | 相槌ターンの台本を作り、話者 B を追加生成（VoiceDesign 固定 ref-wav、ローカル MPS） | 話者 B 一貫性が M3 と同水準（平均 0.8390、最悪 0.6542）|
| 2-4 | ルームトーンを抽出（コーパス原音の無音区間）し、非発話チャンネルに敷く | `pad ⟺ A 無音` の一致率が 98% → **60% 未満** |
| 2-5 | 重なりを入れてタイムラインを再構成 | 重なり区間が全対話に存在し、両チャンネル同時発話のフレームが 0 でない |
| 2-6 | 系列長を測り、100 秒超が必要なら連結の実装可否を判定 | 系列長中央値が **60 秒以上**。100 秒未満なら理由を記録 |
| 2-7 | 新 dataset を tokenize し、manifest と registry を更新 | `tests/test_experiment_assets.py` が通る。step 数が **45** |
| 2-8 | tokenize の全フラグを manifest に記録し、text 統計をテストのゲートにする | フラグを落とすと CI が落ちる |

**2-1 が最重要のゲート**である。row 1-16 が不変なら、
「audio 側の崩壊軌跡（distinct 81 → 5）は text 欠陥では説明できない」が確定する。
変われば、下流の全結論を見直す。

GPU を借りる前に、**借りずに測れるものを全部測る。**

## 第 4 段: GPU 再走（US$25 以内 / 要・打ち切り線の遵守）

第 0〜3 段のゲートをすべて通過してから着手する。

### 設定

| 項目 | M3 | **M3-R** | 根拠 |
| --- | --- | --- | --- |
| 腕 | V-real + V-tts | **V-real のみ** | V-tts の教師が較正帯の外 |
| tempformer LR | 3e-5 | **2e-6** | J-Moshi 自身の fine-tuning 値 |
| depformer LR | 3e-5 | **4e-6** | 同上 |
| warmup | 0 | **入れる** | 既定 0 のまま走っていた |
| 更新範囲 | 全パラメータ | 全パラメータ（`--parameters_to_finetune` は実装済みで、次の変数として保留）| 一度に振る変数を減らす |
| export | epoch 3・5 のみ | **全 epoch** | M3 は最良の epoch 2 を失った |
| seed | 未指定 | **固定** | 全計数が 1 回の抽選だった |
| 生成サンプル数 | prompt あたり 1 | **複数** | 単発抽選では分散が測れない |

### 手順

| # | 作業 | コスト | ゲート |
| --- | --- | ---: | --- |
| 4-1 | forward 1 回で base loss の内訳を測る（bf16 16.74GB、単一 24GB カード） | **US$0.40** | `loss/audio_semantic` と `loss/audio_semantic_user` が分離して出る |
| 4-2 | V-real 学習（45 step / 5 epoch） | US$5 | 起動 assertion が `Num examples 72` / `batch 8` / `steps 45` |
| 4-3 | 全 epoch を変換・export | US$9 | 5 本すべての checksum 一致 |
| 4-4 | 生成（held-out / seen / general30、seed 固定・複数サンプル） | US$4 | 生成数が計画どおり |
| 4-5 | **インスタンスを破棄** | — | `vastai show instances` に該当 ID がない |

**予算の管理**（今回の超過原因 3 つへの対策）

1. 打ち切り線を**経過時間ではなく UTC 時刻**で固定し、`start_date` を毎回読む
2. **export 時間を見積もりに含める**（M3 では 15.4GB あたり約 30 分だった）
3. `tools/experiment_budget.py` を**実行中にも呼ぶ**。今回は借りる前にしか呼んでいない

## 判定基準（第 4 段の完了条件）

第 1 段で改訂した基準を使う。**候補を見る前にここで固定する。**

| # | 条件 | 基準 |
| --- | --- | --- |
| 1 | dataset 一致 | 不一致 0 |
| 2 | tokenize 台帳 | skip が全記録 |
| 3 | 崩壊なし | **音響指標を含む**新検出器で、退化が control 以下 |
| 4 | 話者らしさ | paired mean が正、かつ**較正帯までの距離を有意に閉じる**（区間推定つき）|
| 5 | 明瞭度と turn-taking | 第 3 段で測った control 値を下回らない |
| 6 | 採用理由 | 全 epoch の判断が記録されている |

**条件 3 と 4 はインターロックする**（`tools/likeness_guard.py`）。
崩壊した腕は、話者らしさがいくら高くても条件 4 を通せない。

## この計画が答えられないこと

正直に書いておく。

| 項目 | なぜ答えられないか |
| --- | --- |
| 崩壊の原因が LR かデータ構造か | M3-R は**両方を同時に**直す。分離しない。control を得ることが目的だからである |
| 実音 vs 合成音の比較 | V-tts の教師が帯の外なので、この比較は成立しない。**M2 に戻らない限り答えられない** |
| live 対話での挙動 | マイクを持つ人間が必要。`CLAUDE.md` の「live 対話で崩壊する checkpoint は不合格」は未検証のまま残る |
| 更新範囲を狭めた場合 | 次の変数として保留。M3-R が通れば、そこから初めて比較できる |

**M3-R が不合格でも、それは「原因が特定できた」ことにはならない。**
その場合の次の一手は更新範囲を狭めること（`--parameters_to_finetune tempformer`）であり、
過去のお嬢様 run が約 40 分・tempformer-only で成功している前例がある。
